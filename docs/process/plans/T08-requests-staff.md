# План T08 «Заявки и кабинет сотрудника»

## Контекст
Задача закрывает сценарии 3, 4 и 6 из концепции: заявка проходит путь от студента до деканата и обратно.

Сейчас `/requests` и `/staff` — заглушки из T04.

Что уже есть:
- `activeRequests(ctx)` — блок заявок на «Сейчас» (`repos/requests.ts`);
- `sortRequests` со сроком в рабочих днях (`addBusinessDays`, `services/now.ts`);
- `requireStudent` / `requireStaff`;
- `StatusChip` (тон `seal` — только для «Выдана»);
- в схеме: `Request.seq` (autoincrement), статус `CANCELLED`, `RequestEvent`, `Notification`, `Staff.facultyIds`, `IssuedDocument` с `onDelete: Restrict`;
- в сиде — 8 типов справок с `fields` (text/select) и 8 заявок: у Алисы «Готова» и «Принята», у Тимура «Отклонена», ещё 5 у других студентов, из них МЖ Ирине не видны.

Тесты 1 и 2 в `tests/e2e/security.spec.ts` ждут этой задачи как `test.fixme`.

**Ручной шаг до кода** (`T08-requests-staff.md`): вы включаете security-guidance в `.claude/settings.local.json`. Я в `.claude/` не пишу. Начну код после вашего «да». Если решите работать без security-guidance — скажите, это тоже ответ.

## Решения по умолчанию (поменяю, если скажете)
1. **Уведомление студенту видно уже в T08.** Делаю минимальную `/notifications`: список своих уведомлений, новые сверху, ссылка на заявку. Вкладки, бейдж и «прочитано» остаются в T09. Иначе приёмку «Алиса видит уведомление» нечем проверить. Ссылку из уведомления перед выводом проверяет zod, разрешён только относительный путь `/^\/(?!\/)/` (пункт из T09 делаю сразу).
2. **Двойной клик защищён на двух уровнях.**
   - Кнопка «Отправить заявку» блокируется на время отправки (`useFormStatus`).
   - На сервере форма несёт одноразовый ключ (UUID на каждый показ формы). В схеме — `Request.clientKey` и `@@unique([studentId, clientKey])`. Второй запрос с тем же ключом не создаёт заявку, а ведёт на уже созданную.
   - Это новая миграция: SQL через `prisma migrate diff`, применение — `prisma migrate deploy`. `migrate dev` не используем.
3. **Номер `С-2026-00042`** берём из `nextval` последовательности `seq` (фиксированный SQL без ввода) в той же транзакции, что и создание заявки. Гонок нет, вторая запись не нужна.
4. **Переходы статусов — явная таблица**, всё остальное запрещено:
   - Подана → Принята / Отклонена;
   - Принята → В работе / Отклонена;
   - В работе → Готова / Отклонена;
   - Готова → Выдана.

   Отклонение — только с причиной (zod: от 5 до 500 символов). При «Готова» создаётся `IssuedDocument` с токеном на 128 бит (S7) — его ждёт T10, сид делает так же.
5. **Чужая заявка — настоящий HTTP 404**, приём из T07. Списки — в группах `requests/(list)/` и `staff/(queue)/` со своим `loading.tsx`. У деталей skeleton нет: проверка владельца проходит до начала стрима.
6. **«Сбросить демо»** — только при `DEMO_MODE=1` и только у сотрудника. Сначала подтверждение в `<dialog>`: «Все данные вернутся к исходным, все выйдут из системы». Пересев очищает таблицу сессий, поэтому после него вход заново: ведём на `/login`. Код — `repos/demo.ts` вызывает готовый `runSeed`. Пароли берутся из `process.env` на сервере, как у ночного cron.

## Что делаю

### 1. Данные — `src/server/repos/`
- **`requests.ts` (студент, всё с `studentId: ctx.studentId`):**
  - `requestsOf(ctx)` — активные и архив;
  - `requestByNumber(ctx, number)` — `findFirst({ number, studentId })` с событиями и типом;
  - `createRequest(ctx, input)` — транзакция: `nextval` → `create` + событие SUBMITTED. Если сработал `clientKey` (P2002), возвращаем уже созданную;
  - `cancelRequest(ctx, number)` — `updateMany({ where: { number, studentId, status: "SUBMITTED" } })`, ждём `count === 1`, плюс событие CANCELLED.
- **`staff-requests.ts` (сотрудник, всё с `student.group.program.facultyId in ctx.facultyIds`):**
  - `queueFor(ctx, filters)` — явный `select`: ФИО и группа. Без `recordBookNo`, `calendarToken`, пользователя;
  - `staffRequestByNumber(ctx, number)`;
  - `changeStatus(ctx, { number, from, to, comment })` — транзакция:
    - `updateMany({ where: { number, status: from, факультет } })` с `count === 1` — защита от двух сотрудников разом;
    - событие с `actorUserId = ctx.userId`;
    - уведомление студенту;
    - при READY — `IssuedDocument`.
- **`request-types.ts`** — каталог (публичные поля типа). **`notifications.ts`** — `notificationsOf(ctx)`.

### 2. Логика — `src/server/services/requests.ts` (+ чистые функции с юнит-тестами)
- `fieldsSchema` — zod-описание `RequestType.fields` (text/select). `buildPayloadSchema(type)` строит zod-объект заявки: обязательность, `maxLength`, варианты select, язык — из `type.languages`. Схема собирается на сервере, клиенту уходит только описание полей для отрисовки.
- `formatRequestNumber(year, seq)`, `TRANSITIONS`, `canTransition(from, to)`.
- `timelineOf(request)` — шаги Подана → Принята → В работе → Готова → Выдана: дата пройденных шагов, текущий шаг, ожидаемая готовность (`addBusinessDays(createdAt, slaDays)`, как на «Сейчас»). Для REJECTED и CANCELLED — отдельный финал с причиной.
- `isOverdue(request, now)` — не готова, а срок прошёл.
- Тексты уведомлений по статусу: «Заявка принята», «Справка готова — заберите», «Заявка отклонена» и причина.

### 3. Server Actions — `src/server/actions/requests.ts`, `staff.ts`
- Каждая начинается с `requireStudent()` / `requireStaff()`. Это держит тест-страж `guards.test.ts`.
- Весь ввод проходит через zod. ID студента и сотрудника берутся только из ctx.
- `submitRequest` (useActionState: ошибки полей под полями) → `redirect` на заявку.
- `cancelMyRequest(number)` — если отменить уже нельзя: «Заявку уже взяли в работу — отменить нельзя». Чужой номер — тот же общий ответ без деталей.
- `setRequestStatus` (сотрудник) → `revalidatePath` очереди и карточки.
- `resetDemo` (сотрудник + `DEMO_MODE=1`).

### 4. Экраны студента — `src/app/(student)/requests/`
- **`(list)/page.tsx` — «Заявки».**
  - Кнопка «Заказать справку» — единственная заливная на экране.
  - «Активные» (READY первой, как на «Сейчас») и «Архив» (Выдана, Отклонена, Отменена) — строками под линиями: тип, номер, `StatusChip`, «готова к 12 нояб.» или дата.
  - Пусто: «Заявок пока нет — закажите первую справку» и кнопка.
  - Свои skeleton и `error.tsx`.
- **`new/page.tsx` — «Заказать справку»:**
  - каталог — простой список типов: название, описание, срок «2 рабочих дня», языки. Мастер «Зачем?» — в T10;
  - `?type=study_en` (zod) открывает форму: поля из `fields`, язык справки (радио, если языков больше одного), «Отправить заявку».
  - Форма — клиентский компонент, ошибки сервера показываются у полей.
- **`[number]/page.tsx` — заявка** (без skeleton, чужая → 404):
  - `RequestTimeline` — вертикальные шаги. Пройденный — галочка и дата, текущий — выделен, будущий — тихий. Смысл передан текстом и иконкой, не только цветом;
  - «Ожидаемая готовность: пт, 13 нояб.»;
  - что указали в заявке;
  - комментарии деканата у шагов;
  - «Отменить заявку» — только у SUBMITTED, через подтверждение.

  У READY: «Справка готова — заберите в деканате, кабинет …». PDF с QR — в T10, кнопку не рисую.
- **`(student)/notifications/page.tsx`** — минимальный список (решение 1).

### 5. Кабинет сотрудника — `src/app/(staff)/staff/`
- **`(queue)/page.tsx` — «Очередь заявок».**
  - Фильтры ссылками через `searchParams`, разбирает zod: статус (по умолчанию «В работе у деканата» — Подана, Принята, В работе), факультет (только свои), тип.
  - Сортировка — по сроку: просроченные первыми.
  - Строки: срок («просрочена на 2 дня» — `danger` + иконка + текст), номер, тип, студент (Фамилия И. О., группа), статус.
  - На десктопе плотнее, на 360px — те же строки, перенос по ширине. Без таблицы — она ломается на телефоне.
- **`requests/[number]/page.tsx` — карточка** (без skeleton, чужой факультет → 404):
  - студент: ФИО, группа, факультет, курс;
  - тип, язык, поля заявки;
  - история событий с комментариями;
  - **действия** — только разрешённые переходы, кнопками с глаголами: «Принять», «Взять в работу», «Готова», «Выдана», «Отклонить». Комментарий необязателен, у отклонения обязательна причина (отдельный `<dialog>`);
  - после действия — статус обновляется на месте.
- **«Сбросить демо»** — в шапке кабинета, только при `DEMO_MODE=1` (решение 6).
- В навигации сотрудника «Заявки» подсвечены и на карточке.

### 6. Тесты
- **Юнит:**
  - `buildPayloadSchema`: обязательные поля, `maxLength`, неизвестный вариант select, лишние поля отброшены, язык не из списка;
  - `fieldsSchema` отбрасывает битое описание;
  - номер, `canTransition` (все пары), `timelineOf` (обычный путь, отклонение, отмена, срок по рабочим дням), `isOverdue`, проверка ссылки уведомления.
- **Интеграция** (`tests/integration/requests.test.ts`):
  - создание: номер по порядку; повтор с тем же `clientKey` — та же заявка;
  - отмена чужой — `count 0`, статус прежний;
  - отмена не-SUBMITTED — отказ;
  - переход «из неверного статуса» — отказ;
  - очередь Ирины — без МЖ, без `recordBookNo` в ответе;
  - смена статуса создаёт событие и уведомление; READY создаёт `IssuedDocument`.
- **e2e:**
  - **Приёмка:** Алиса подала «Справку об обучении на английском» → номер и «Подана» → Ирина в очереди нашла её → «Принять» → «Взять в работу» → «Готова» → Алиса видит уведомление «Справка готова» в `/notifications` и статус «Готова» в заявке;
  - **двойной клик** по «Отправить заявку» → ровно одна новая заявка (считаем строки списка до и после, у Алисы);
  - **`security.spec.ts`:** тесты 1 и 2 из fixme становятся обычными:
    - 1 — номер заявки Алисы берём из её списка; Тимур получает 404, данных заявки в HTML нет;
    - 2 — Тимур вызывает Server Action отмены с номером Алисы (через форму на его странице с подменённым полем) → ошибка; под Алисой статус прежний;
  - Ирина не видит заявки студентов МЖ (в очереди и по прямому номеру → 404);
  - отклонение без причины → ошибка у поля;
  - отмена своей SUBMITTED;
  - битые фильтры очереди → 200;
  - 360px при тексте 200% — список, форма, заявка, очередь, карточка;
  - новые маршруты — в общий обход axe.
  - «Сбросить демо» в e2e не нажимаю: он стирает сессии всего набора. Проверяю, что кнопки нет без `DEMO_MODE`, а Server Action отказывает студенту (юнит и интеграция).
- Новые spec — `--repeat-each=3`, потом весь набор.

## Риски
- **Две мутации разом** (два сотрудника, двойной клик) — `updateMany` с ожидаемым `from` и `count === 1`, `clientKey`.
- **Утечка между факультетами** — фильтр в каждом запросе сотрудника, e2e на МЖ, интеграция на `select`.
- **«Сбросить демо» на проде** выкидывает из системы всех, в том числе жюри. Поэтому кнопка спрятана за `DEMO_MODE` и подтверждением, а в отчёте будет пометка.
- **Объём:** это самая большая задача ядра. Порядок: данные → студент → сотрудник → уведомления → тесты. Коммичу после каждого шага, каждый коммит собирается сам (урок T07).
