# Red-team T13 (часть В): атака на свой сайт

**Дата:** 10.11.2026 · **Исполнитель:** Claude Code (Opus 4.8), отдельная сессия с чистым контекстом «атакующего».
**Цель:** ИИ в роли внешнего злоумышленника пытается вскрыть «Протокол» и доказывает, что защита держится не на словах. Материал для жюри (критерии «Имплементация» и «Масштаб ИИ»).

## Границы (соблюдены)

- Только наш сайт, **локальная прод-сборка** (`pnpm build` → `pnpm start`, `node .next/standalone/server.js`) против Docker-Postgres, база `protokol_e2e`. VPS **не трогали** (ждёт отдельного «да» человека на адрес и окно).
- Чужие хосты (GigaChat, GHCR, Docker Hub, GitHub) не трогали. Помощник тестировали с `ASSISTANT_PROVIDER=faq` — без обращений к GigaChat.
- Без DoS и флуда: лимиты и блокировки проверяли единичными запросами; перебор времени ответа — по 20 запросов на вариант с паузой 1 с, каждый с собственным IP (своя пара «логин + IP», блокировка не вмешивается).
- Только тестовые аккаунты и вымышленные данные. Сессии «атакующего» заводили прямо в БД (как `tests/e2e/helpers/temp-student.ts`), после прогона удаляли.
- Защиты агента (`guard.mjs`, `deny`, классификатор) не обходили. `.env` не читали.
- Проверено в **двух конфигурациях**: `DEMO_MODE=1` (демо-вход открыт) и `DEMO_MODE=0` (демо-вход закрыт). `DEMO_MODE` берётся из `.env` при старте standalone, поэтому для режима «без демо» переменную переопределяли явно (`DEMO_MODE=0`).

Выход удаляет запись в БД, «выйти на всех устройствах» и смена пароля сбрасывают все сессии.
**Тесты:** `security.spec.ts` блок «вход и сессии (T03)» — поддельная cookie, выход, «на всех устройствах», атрибуты cookie.

## Группа 4. Вход

| Что сделали | Что получили | Вывод |
|---|---|---|
| **Время ответа:** существующий логин (`student.savelev`, неверный пароль) vs несуществующий, по 20 запросов, свежий IP, пауза 1 с | existing: среднее **427.5 мс**, медиана 426.3; ghost: среднее **427.5 мс**, медиана 425.2. **Разница средних — 0 мс** | защита (нет оракула «есть ли логин» по времени) |
| 6 неверных паролей, один логин + IP | invalid×4, затем **locked** на 5-й и 6-й попытке | защита (блок на 5 мин) |
| Обход блокировки регистром/пробелами: `  Student.Savelev  `, `STUDENT.SAVELEV`, `student.savelev ` с того же IP | все три — **locked** (нормализация логина: trim + lowercase → тот же ключ) | защита (обхода нет) |
| DoS-ввод: пароль 1 МБ | **11 мс** (argon2 ~426 мс не запускается), Next отклоняет тело >1 МБ | защита |
| Перечисление по тексту: существующий vs несуществующий | оба — одинаковый ответ `invalid` («Неверный логин или пароль») | защита |

**Почему держится:** несуществующий логин проверяется фиктивным argon2id-хешем (считается один раз при старте) — время ответа такое же, как у неверного пароля. Блокировка — по паре `sha256(логин+IP)`, попытка «занимается» атомарно одним `INSERT … ON CONFLICT` до argon2 (параметры через `$queryRaw`, не склейка строк). Пароль длиннее 128 символов не хешируется (`loginLimitsSchema`) — дешёвая DoS закрыта.
**Тесты:** `security.spec.ts` тест 7 (блокировка), «одна и та же ошибка для нет логина и неверный пароль».

## 5 атак на GigaChat (prompt injection) — не проводились

Задача допускает 5 инъекций в живой GigaChat (чужие данные, системный промпт, ключ, действия) **только при наличии ключа в `.env` и доступности шлюза**. Не проводили, потому что:
1. Дословная граница человека: «чужие хосты (GigaChat, GHCR, Docker Hub, GitHub) не трогаем».
2. Шлюз GigaChat (`ngw…:9443`) из этого окружения недоступен (отметка T12, 07.11).
3. `.env` не читаем — наличие ключа не проверяли.

Важно: S8 защищает **независимо от провайдера**. Даже с живой моделью инъекция не вскроет чужие данные — их нет в промпте (см. группу 7, провайдер `faq`: контекст-изоляция и отказ работают одинаково). Живую проверку GigaChat оставляем человеку (VPS с доступом к шлюзу).

## Ложные тревоги харнеса (разобраны)

1. **«Поддельная/мусорная cookie → HTTP 200»** — ложное. Next отдаёт редиректы Server Component телом с кодом 200 (`NEXT_REDIRECT;replace;/login;307`), браузер по нему уходит на `/login`. В теле — только инертные подписи оболочки (`Учёба`, `Разделы кабинета` — ярлыки навигации без данных), защищённого содержимого нет (`Очередь заявок`, `средний`, `рейтинг` — отсутствуют). То же свойство использует `security.spec.ts` (проверяет `NEXT_REDIRECT` в теле).
2. **«XSS: `onerror` в теле → true»** — ложное. Строка `onerror=alert()` присутствует только внутри экранированного текста `<img…>` (узел text в потоке RSC), живого тега `<img onerror>` нет. React экранирует текстовые узлы; `<` и `>` закодированы.

## Замечание по сборке (не уязвимость, процесс)

Первая прод-сборка, запущенная в фоне параллельно с подготовкой БД, вышла неполной: в `.next/standalone` не попали `content/faq/**` (нужны помощнику) и манифесты клиентских ссылок — `/notifications` отвечал 500, `/api/assistant` — `{"t":"error"}`. Чистая пересборка это исправила (в standalone появились `content/faq` и 25 манифестов). Это артефакт гонки сборок, а не прода: Dockerfile и `outputFileTracingIncludes` копируют нужное; e2e (`notifications.spec`, `assistant.spec`) проходят на свежей сборке. Урок — не запускать `pnpm build` параллельно с операциями над БД/`.next`.
