# CLAUDE.md — «Протокол», цифровой деканат (концепт)

Ты — ведущий разработчик прототипа личного кабинета студента для конкурса «Цифровой деканат будущего».
Вуз-пример — МГИМО. Это **концепт для конкурса, не официальный сервис вуза**.

Команда: человек (постановка задач, проверка, ручные шаги) + Claude Code (код).
Общение, комментарии к коммитам и тексты интерфейса — на русском. Идентификаторы в коде — на английском.

## Железные правила

> Проверка доступа — на сервере (`requireStudent`, репозитории). `proxy.ts` — только редирект для удобства.
> `requireStudent()` / `requireStaff()` обёрнуты в React `cache()` и вызываются **в каждой** page, Server Action и route handler.
> Проверка в layout не защищает: layout не перерисовывается при клиентской навигации и рендерится параллельно со страницей.
> Тест-страж (`tests/unit/guards.test.ts`) падает, если `page.tsx` в `(student)`/`(staff)` не вызывает guard.

**Безопасность** (подробно — `docs/05-security.md`):
- Данные студента читаются ТОЛЬКО через `src/server/repos/*` с `ctx.userId` из сессии. ID студента никогда не берётся из URL, формы или query.
- Чужой ресурс → `notFound()` (404), а не 403: не подтверждаем существование.
- Пароли — только argon2id. Секреты — только в `process.env` на сервере, никогда с префиксом `NEXT_PUBLIC_`.
- Любой ввод проходит через zod-схему на сервере.
- Новый маршрут с данными = новый e2e-тест «студент B не видит данные студента A».

**Данные**: только вымышленные. Никаких реальных ФИО преподавателей и студентов МГИМО, реальных номеров, логотипа МГИМО.
Названия факультетов и здания — можно (это открытые реалии).

**Маркировка концепта**: на странице входа и в футере всегда видна плашка
«Концепт для конкурса. Не является официальным сервисом МГИМО. Все данные вымышлены.»

**Интерфейс**:
- Mobile-first. Сначала верстаем 360px, потом расширяем. Проверяй 360, 390, 768, 1280.
- У каждого экрана с данными есть 4 состояния: загрузка (skeleton), пусто, ошибка, данные.
- Нужное — за 1–2 касания из нижней навигации.
- Только компоненты и токены из `docs/04-design.md`. Не изобретай новые цвета.

**Код**:
- Server Components по умолчанию; `"use client"` — только где нужна интерактивность.
- Мутации — Server Actions с zod + проверкой роли + `revalidatePath`.
- Никаких `any`. Никаких закомментированных кусков кода в коммитах.
- Новая зависимость → `pnpm add -E` (точная версия) + строка в «Лицензии» `03-architecture.md`.
- Маленькие коммиты: `feat(schedule): …`, `fix(auth): …`, `docs: …`.

- [ ] Затронутые сценарии проходят в e2e, включая проект `mobile-360`

- [ ] Для задач с данными/входом: `/security-review` чистый (и security-guidance, если он включён)
- [ ] Прогнаны субагенты: `security-reviewer` (если трогали данные/вход), `ux-reviewer` (если трогали UI)
- [ ] Запись в `docs/process/journal.md` (команда `/log`)

## Журнал процесса — обязательно

Жюри оценивает, как шла работа с ИИ (отдельный критерий, 10 баллов). Поэтому:
- После каждой задачи — `/log`: что просили, что получилось, что пришлось исправлять.
- Если ты (ИИ) ошибся и это поймали тесты/ревьюер/человек — запись в `docs/process/ai-errors.md`.
- Если человек сделал что-то руками — отметка «вручную» в журнале.
- Ключевые промпты человек копирует в `docs/process/prompts.md`.

## Чего не делать

- Не подключаться к реальным системам МГИМО и не парсить закрытые данные. Открытое расписание парсить можно, но в прототипе используем сид.
- Не добавлять зависимости без причины; для новой — указать лицензию в `docs/03-architecture.md` → «Лицензии».
- Не трогать `docs/05-security.md` без явной просьбы человека.
